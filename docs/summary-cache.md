# 하루 요약 캐시 (2026-08-03)

"저번주 정리해줘" 같은 다중 날짜 질문이 매번 하루치를 처음부터 다시 요약해서
느렸던 걸, 지난 날의 요약을 미리 만들어두고 조회만 하도록 바꾼 기록.

## 배경

- 원래 문제: 7일치 정리 질문 하나에 `browse()`(0.3~0.8초) + LLM 호출(약 1초)이
  날짜마다 들어가서 7초 넘게 걸림. `asyncio.gather`로 LLM 호출은 동시에
  돌렸지만(도큐먼트: `streaming-and-async.md`), `browse()`가 동기 호출이라
  이벤트 루프를 막아서 그 부분은 여전히 순차 실행됐다(실측: 7일 × 0.3~0.8초
  ≈ 2초가 이 병목)
- 핵심 관찰: 지난 날의 화면 기록은 더 자라지 않는다. 어제 요약은 오늘 물어도
  다음 주에 물어도 같은 답이어야 하는데, 매번 새로 계산하고 있었다
- 접근: 요약을 "질문 올 때 즉석에서 계산"이 아니라 "색인 직후 미리 계산해서
  저장, 질문 오면 조회만"으로 전환

## 구조

### 저장소 — `summary_cache.py`

`chroma/` 안에 별도 sqlite 파일(`summary_cache.sqlite`)을 둔다. chromadb가
관리하는 `chroma.sqlite3`(벡터 검색용, 391M)에 직접 얹지 않은 이유:
chromadb API를 거치지 않고 그 안에 우리 테이블을 끼워 넣으면 라이브러리
내부 구조가 바뀔 때 같이 깨질 위험이 있고, "날짜 -> 요약 문자열" 키-값
저장이 전부라 벡터 임베딩이 필요한 chromadb를 쓸 이유도 없다.

```sql
CREATE TABLE day_summary (
    date        TEXT PRIMARY KEY,
    summary     TEXT NOT NULL,
    event_count INTEGER NOT NULL,
    model       TEXT NOT NULL,
    created_at  TEXT NOT NULL
)
```

- `model` 컬럼: `CHAT_MODEL`을 바꾸면(gemini <-> claude) 말투/형식이 달라지므로
  날짜만이 아니라 날짜+모델로 조회한다 — 모델 전환 시 옛 요약이 섞여
  들쭉날쭉해지는 걸 막는다
- `date < today_str()` 문자열 비교로 "지난 날인가"를 판단한다 — `YYYY-MM-DD`는
  ISO 포맷이라 문자열 사전순 비교가 날짜 비교와 동일하다(datetime 파싱 불필요)
- `get()`/`put()` 둘 다 함수 맨 앞에서 `is_cacheable_day()`를 확인 — "오늘은
  캐시 대상 아님" 규칙이 조회/저장 양쪽에 동일하게 박혀 있어 한쪽만
  빼먹는 실수가 구조적으로 안 남는다

### 캐시 연결 지점 — `summarize.py`의 `summarize_day()`

```python
plain = _is_plain_day_request(app, hour_start, hour_end, site, history, question)
if plain:
    cached = summary_cache.get(date, CHAT_MODEL)
    if cached is not None:
        return cached          # browse()까지 통째로 건너뜀

events = browse(date, app, hour_start, hour_end, site)   # 캐시 미스일 때만 도달
...
if plain:
    summary_cache.put(date, result, raw_count, CHAT_MODEL)
```

캐시 체크를 `browse()` **앞에** 둔 게 핵심 — `browse()` 자체가 0.3~0.8초짜리
비용이라, 뒤에 뒀으면 LLM 호출만 아끼고 조회 비용은 그대로 남았을 것.

`_is_plain_day_request()`는 화이트리스트가 아니라 **블랙리스트**로 짰다("이런
조건이면 캐시 쓰지 마라"를 나열, 다 안 걸리면 캐시 허용). 나중에 필터가
추가됐는데 이 함수에 반영을 깜빡하면, 화이트리스트 방식은 "캐시가 잘못
적중"하는 사고로 이어지지만 블랙리스트 방식은 "캐시를 안 쓰고 매번 새로
계산"하는 정도로만 실패한다 — 느려지는 건 티가 안 나지만 틀린 답은 바로
티가 나므로, 실패 방향을 안전한 쪽으로 고정한 것.

캐시를 건너뛰는 조건(전부 블랙리스트 항목):
- app/site/hour 필터가 걸린 질문
- 멀티턴 history가 있는 질문 (`streaming-and-async.md`의 멀티턴 기능과 연결)
- 질문에 "자세히"/"쉽게"/"간단히" 등 분량 조절 키워드가 있는 질문
  (`SUMMARY_DETAIL_KEYWORDS`, config.py)
- **오늘 날짜** — 기록이 계속 자라므로 항상 새로 계산, 저장도 안 함

### 미리 채우기 — `build_summary_cache()` + CLI

```bash
uv run python -m screenlog.summarize          # 아직 없는 지난 날짜만 생성
uv run python -m screenlog.summarize --stats  # 캐시 상태 확인
```

`asyncio.Semaphore(concurrency=5)`로 동시 LLM 호출 수를 제한한다 —
`asyncio.gather`를 제한 없이 쓰면 캐시 채울 날짜가 많을 때(예: 90일 백필) 한
번에 다 쏴서 레이트리밋에 걸릴 수 있다.

색인(`index.py`)과 분리된 별도 명령으로 둔 이유: 색인은 LLM 없이 임베딩만
하는 단계라 API 키/네트워크가 안 필요하다. 색인 안에 LLM 호출을 끼워 넣으면
게이트웨이가 죽었을 때 색인까지 같이 실패한다.

### 배포 파이프라인 — `distribution/mac/menubar/app.py`

동기화 순서를 **색인 → 요약 생성 → 서버 전송(rsync)** 으로 바꿨다. 요약
캐시 파일이 `chroma/` 안에 생기므로 rsync보다 먼저 돌아야 서버로 같이
넘어간다. 요약 생성 실패는 색인/rsync 실패와 다르게 처리 — `return`으로
막지 않고 다음 단계로 넘어간다. 게이트웨이가 죽어 요약을 못 만들어도 색인된
벡터 데이터 자체는 정상이니 전송까지 막을 이유가 없고, 요약 캐시가 없으면
서버는 그냥 즉석 계산 경로로 자동 대체되어 느려질 뿐 깨지지 않는다.

## 과정에서 발견하고 고친 버그 — 프론트 타이핑 애니메이션

백엔드를 빠르게 만드니 **타이핑 효과가 새 병목**이 됐다. 캐시 적중으로
4,600자 답이 즉시 도착해도, `streaming-and-async.md`에서 만든 타이핑
애니메이션이 15ms마다 고정 2글자씩만 그려서 화면에 다 뜨는 데 30초 넘게
걸렸다 — 백엔드 개선분을 애니메이션이 통째로 잡아먹은 것.

고친 방식: 한 틱에 그리는 글자 수를 "남은 글자 수 / TYPE_TICKS"로 계산해서,
답이 길든 짧든 체감 시간이 비슷해지게 함. 단, 이 계산이 **매 틱마다 남은
양 기준으로 다시 이뤄져서** 등비수열처럼 감쇠한다 — `TYPE_TICKS=90`으로
두면 "90틱 만에 끝나겠지"라는 예상과 달리 실제로는 약 380틱(≈5.7초) 걸림을
실측으로 확인했고, 20으로 낮춰 4,600자가 약 113틱(≈1.7초)에 수렴하도록
조정했다. 스트리밍(검색 intent, 토큰이 조금씩 옴)에는 영향 없음 — 매 틱
남은 양이 작아서 자연히 최소값(2글자)으로 떨어짐을 확인(점진 갱신 166회).
