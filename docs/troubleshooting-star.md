# 트러블슈팅 기록 (STAR)

화면 기록 RAG를 만들면서 겪은 문제와 해결 과정. 숫자는 전부 실행 로그에서 그대로 가져왔다.

---

## 1. 프레임 중복으로 검색이 무의미해지는 문제

**Situation**
screenpipe는 3~6초 간격으로 화면을 캡처하는데, 화면이 안 바뀌는 동안에는
프레임마다 텍스트가 사실상 동일하다. 프레임 1개를 문서 1개로 그대로 색인했더니
무엇을 검색해도 가장 자주 반복되는 텍스트(사이드바 메뉴 등)가 상위에 잡혔다.
검색 결과에 "Collapse sidebar / 검색 / 홈" 같은 UI 요소만 계속 보이는 상태였다.

원본 규모는 하루치(2026-07-28) 기준 프레임 2,905개 / 20,251,452자였다.

**Task**
프레임이 아니라 "하나의 활동"을 검색 단위로 만들어야 했다. 다만 다음 두 가지를
동시에 만족해야 했다.
- 단순히 이어붙이면 글자 수가 전혀 줄지 않는다 (문서만 거대해짐)
- 앱 단위로 통째로 합치면 "언제 있었던 일인지"가 뭉개진다

**Action**
- 앱+창이 같은 **연속** 프레임만 하나의 그룹으로 묶었다. 시간이 떨어진 동일 앱은
  별도 그룹으로 둬서 시각 정보가 뭉개지지 않게 했다.
- 그룹 안에서 이미 등장한 줄을 `seen` 집합으로 추적해 중복 줄만 제거했다.
- 창 제목이 안 바뀌는 앱(Claude, Code)에서 서로 다른 작업이 한 덩어리가 되는 문제가
  있어, 그룹 안에서도 다음 조건이면 이벤트를 끊게 했다.
  - 연속 프레임 간 자카드 유사도(`overlap`)가 0.3 미만 — 화면이 통째로 바뀜
  - 누적 글자 수가 2,000자 초과 — 긴 세션이 계속 불어남
- 끊는 지점은 글자 중간이 아니라 **프레임 경계**로 잡아, 각 이벤트가 실제 프레임
  구간에 대응하도록 했다.

**핵심 시행착오 — `seen`을 언제 비우는가**

이벤트를 끊을 때 `seen`도 같이 초기화했더니 글자 수가 오히려 폭증했다.
화면 텍스트는 앞부분이 그대로 유지되면서 몇 줄만 늘어나는(prefix-growing) 구조라,
`seen`을 비우는 순간 다음 이벤트가 이미 내보낸 수천 자를 통째로 다시 담았다.

| `seen` 스코프 | 총 글자 |
|---|---|
| 이벤트마다 초기화 | 3,045,016자 |
| **그룹 전체에서 유지** | **821,501자** |

**4배 차이**였다. 이벤트를 끊는 것은 *자르는 위치*만 정하는 것이고,
*중복 제거 기억*은 그룹 내내 유지되어야 한다는 걸 여기서 확인했다.

> 중복 제거 로직에서는 "무엇을 제거하는가"보다
> **"제거 기억을 언제 버리는가"** 가 더 민감하다.

**Result**
하루치(2026-07-28) 기준 프레임 2,905개 / 20,251,452자 → 이벤트 1,303개 /
4,358,293자로 **약 79% 감소**. 실제 색인 시점에는 캡처가 계속 진행 중이어서
1,313개 이벤트로 저장됐다.

무작위 표본을 직접 읽었을 때 "이때 이거 했지"가 읽히는지로 정성 검증도 통과했다.

## 2. 전량 재임베딩으로 실험 자체가 불가능해지는 문제

**Situation**
색인 대상을 하루(2026-07-28)에서 전체 7일(2026-07-22~28)로 늘리는 시점이었다.
하루치 색인만으로도 이벤트 1,313개(4.36M자) 임베딩에 **12분 50초**가 걸렸다.
7일이면 1시간을 훌쩍 넘기는데, 문제는 시간 자체가 아니라 다음 두 가지였다.

- 중간에 실패하면 그때까지 임베딩한 게 전부 날아간다
- 정제 파라미터를 조금만 바꿔도 전체를 다시 태워야 해서, 하루에 여러 번
  재실험하는 게 불가능해진다

임베딩 배치 크기도 제약이었다. 기본값(32)으로 돌리면 화면 텍스트가 길어서
MPS 메모리가 터졌고, `EMBED_BATCH_SIZE=4`로 낮춘 대가가 이 소요 시간이었다.

**Task**
날짜가 늘어나도 이미 색인된 날짜는 다시 임베딩하지 않고, 중간에 실패해도
그 이전 날짜 결과는 보존되는 색인 방식이 필요했다.

**Action**
- **색인 단위를 하루로 쪼갰다.** `index_date(date)`를 최소 단위로 두고,
  하루가 끝날 때마다 즉시 chroma에 저장하게 했다.
- **이벤트 id를 내용 해시로 만들었다.** `app + window + start + text`를 SHA1로
  해싱해서, 같은 이벤트는 몇 번을 재실행해도 같은 id가 나오도록 했다.
  순번(0, 1, 2...)을 쓰면 실행할 때마다 id가 달라져서 재시도가 곧 중복 생성이 된다.
- **`insert` 대신 `upsert`를 썼다.** 위의 멱등 id와 짝을 이루는 선택으로,
  재실행 시 에러 없이 덮어쓰기가 된다.
- **이미 색인된 날짜를 조회해 건너뛰게 했다.** `indexed_dates()`가 chroma
  metadata의 `date` 필드를 확인하고, `index_all()`은 없는 날짜만 순서대로 처리한다.

**Result**
07-22~07-27 배치 실행 로그:

| 날짜 | 이벤트 수 |
|---|---|
| 07-22 | 1,009 |
| 07-23 | 1,533 |
| 07-24 | 2,021 |
| 07-25 | 74 |
| 07-26 | 18 |
| 07-27 | 2,844 |
| 07-28 | 건너뜀 - 이미 있음 |

전체 8,812개 이벤트 누적. 이미 색인돼 있던 07-28을 재임베딩 없이 정확히 건너뛰는
것을 실행 로그로 확인해, 멱등성 설계가 실제로 동작함을 검증했다.

부수적으로 07-25(74개), 07-26(18개)은 다른 날의 1/20~1/100 수준이었는데,
원본 프레임을 확인해보니 각각 106개 / 21개로 캡처 자체가 적었다.
정제 로직 문제가 아니라 그 기간에 screenpipe가 거의 안 돌았던 것으로,
데이터 이상을 정제 버그로 오인하지 않도록 원본까지 되짚어 확인했다.

## 3. 프롬프트 크기가 제어되지 않아 LLM 토큰 비용이 튀는 문제

**Situation**
평가 세트(15문항)를 돌린 뒤 LLM API 사용량이 예상보다 크게 늘었다.
호출 횟수 자체는 17번(테스트 2 + 평가 15)으로 많지 않았기 때문에,
호출당 프롬프트 크기를 의심하고 실측했다.

색인된 이벤트 8,812개의 크기 분포는 다음과 같았다.

| | 글자 수 |
|---|---|
| 중앙값 | 1,270 |
| 평균 | 1,848 |
| 상위 10% | 3,485 |
| **최대** | **36,870** |

중앙값과 최대값이 **29배** 차이 났다. 정제 단계에서 이벤트를 끊는 기준
(`MAX_EVENT_CHARS=2000`)은 프레임 경계에서만 검사하기 때문에, 프레임 하나가
통째로 크면 그 이벤트는 상한을 크게 초과한 채로 만들어진다.

**Task**
`build_context()`가 검색 결과 `k=5`개의 본문을 **아무 제한 없이** 프롬프트에
그대로 넣고 있었다. 큰 이벤트가 우연히 몇 개 걸리는 것만으로 프롬프트가 수십 배로
부푸는 구조라, 비용이 질문 내용에 따라 예측 불가능하게 튀었다.
이론상 최악은 36,870자 × 5 = 약 18만 자였다.

**Action**
- `CONTEXT_CHARS_PER_HIT = 1500`을 설정에 추가하고, `build_context()`에서
  근거 하나당 글자 수를 잘라내도록 했다. 잘린 경우 `…(잘림)` 표시를 붙여
  LLM이 뒷부분이 생략됐음을 알 수 있게 했다.
- 상한값은 이벤트 크기 분포에서 정했다. 중앙값(1,270자)보다는 크게 잡아
  대부분의 이벤트는 손실 없이 통과시키고, 상위 10%(3,485자) 이상의
  비정상적으로 큰 이벤트만 잘리도록 1,500자로 뒀다.
- 검증은 **LLM 호출 없이** 했다. 임베딩은 로컬(bge-m3)이므로 `search()`로
  실제 검색만 수행하고 `build_context()` 결과 길이만 재서, 비용 조사 과정에서
  추가 비용이 발생하지 않게 했다.

**Result**
실제 평가 세트 15문항, k=5 기준 측정값:

| | 수정 전 | 수정 후 |
|---|---|---|
| 합계 | 228,970자 | **95,693자 (−59%)** |
| 질문당 평균 | 15,264자 | **6,379자** |
| **최대 (단일 질문)** | 46,129자 | **7,846자** |

평균이 절반 이하로 줄어든 것보다, **최대값이 46,129자에서 7,846자로 묶인 것**이
핵심이다. 비용의 상한이 질문 내용과 무관하게 `k × 1500자`로 고정되면서,
"어떤 질문이 걸리느냐"에 따라 비용이 튀는 문제가 사라졌다.

부수적으로 얻은 교훈: **임베딩(로컬)과 LLM 호출(API)의 비용 구조가 완전히 다르다.**
13분씩 걸린 색인 작업은 API 비용이 0이었고, 몇 초 만에 끝나는 질의 응답이
실제 비용의 전부였다. 소요 시간과 비용이 반비례하는 구조라, 체감으로
비용을 짐작하면 틀린다.

## 4. 라우팅 LLM이 없는 앱을 지어내는 문제

**Situation**
`router.py`에 hybrid 라우팅(규칙 우선, 실패 시 LLM 폴백)을 추가한 뒤, "LLM 호출이
너무 잦아지는 거 아니냐"는 우려가 있었다. 실제 빈도를 확인하려고 `router.py`에
카운터(`get_stats()`)를 추가하고, 사전에 없는 표현 3개(q16~q18: "화상회의 앱",
"파일 관리자", "쉘")를 질문 세트에 넣어 `eval/eval_routing.py`로 라우팅만
(생성 없이) 18문항을 돌렸다.

**Task**
호출 빈도를 재는 게 목적이었는데, 결과표를 읽다가 다른 문제가 먼저 보였다.
app 일치가 14/18로, 새로 추가한 3문항이 아니라 **기존에 이미 성공하던 4문항**
(q11, q12, q14, q15)에서 실패가 나왔다. 전부 앱 이름을 전혀 언급 안 한 순수
내용 질문(semantic/keyword 카테고리)이었다.

**Action**
직접 `route()`를 호출해 원인을 확인했다.

```
"RAG 파이프라인 설계에 대해 무슨 얘기를 했어?" -> {"app": "Code", ...}
"임베딩 모델이나 벡터 검색에 대해 뭘 찾아봤어?" -> {"app": "Google Chrome", ...}
"chromadb에 대한 내용을 찾아줘"              -> {"app": "Google Chrome", ...}
"screenpipe에 대해 뭘 알아봤어?"              -> {"app": "Google Chrome", ...}
```

규칙이 app/hour/date를 하나도 못 찾으면 무조건 LLM에게 넘기는데, LLM이 "이런
내용이면 아마 이 앱에 있겠지"라고 **없는 정보를 추측**했다. 원래 프롬프트가
"app: 다음 중 하나 또는 null"이라고만 돼 있어서, null을 골라도 되는 상황을
구체적으로 알려주지 않았다.

이 4문항은 필터 없이 이미 100% 성공하던 질문들이다. 그대로 라우팅에 연결했으면
잘 되던 검색을 라우팅이 오히려 망가뜨릴 뻔했다 — 호출 빈도를 재려던 카운터가
비용 문제보다 먼저 정확도 버그를 잡아낸 것이다.

`LLM_PROMPT`에 조건을 명시적으로 추가했다.

```
app: 다음 중 하나 또는 null - {apps}
    질문이 특정 앱이나 앱 종류(에디터, 메신저, 화상회의 등)를 가리킬 때만 채운다.
    "~에 대해 뭘 찾아봤어", "~얘기했어"처럼 내용을 묻는 질문은 앱을 추측하지 말고 null로 둔다.
```

**Result**

| | 수정 전 | 수정 후 |
|---|---|---|
| app 일치 | 14/18 | **17/18** |

q11, q12, q15는 정확히 null로 고쳐졌다. **q14("chromadb")만 여전히 Google Chrome을
지어낸다** — "chromadb"라는 글자가 "Chrome"과 형태적으로 겹쳐서, 지시문을 줘도
그 착각을 못 이긴다. 미해결로 남겨뒀다. 개선 후보로 "결론(JSON)부터 내지 말고
판단 근거를 먼저 글로 쓰게 한 뒤 JSON을 내게 하는" reasoning 방식을 검토했으나
아직 적용하지 않았다.

애초에 재려던 호출 빈도(9/18, 50%)는 이번 수정으로 줄지 않았다 — "규칙이
못 찾았다"는 것이 "필터가 있는데 규칙이 놓쳤다"와 "애초에 필터가 필요 없는
질문이다"를 구분 못 하기 때문이다. 다만 라우팅 LLM 호출 하나가 284자로 생성
호출 평균(6,379자)의 1/22 수준이라, 빈도가 높아도 당장 손해는 크지 않다고 보고
`get_stats()`로 실사용 빈도만 지켜보기로 하고 넘어갔다.

> 카운터를 달아서 재려던 것과 실제로 발견한 문제가 달랐다. 비용을 재려다
> 정확도 버그를 먼저 잡았다 — 뭘 재려고 계측을 붙이든, 계측 결과 자체를
> 있는 그대로 읽어보는 게 항상 남는다.

## 5. 하루 요약 프롬프트가 이벤트 개수 상한 없이 100만 자를 넘는 문제

**Situation**
4단계(여러 날짜 조회)를 만들면서 `summarize_day()`가 `browse()`로 그 날짜의
이벤트를 전부 가져와 프롬프트에 넣게 짰다. `ask()`(단일 날짜 검색)엔 이미
`CONTEXT_CHARS_PER_HIT`로 이벤트 하나당 글자 상한이 있었지만, `summarize_day()`엔
**이벤트 몇 개까지 넣을지에 대한 상한이 아예 없었다.**

**Task**
"LLM 호출은 어디서 일어나고 토큰은 어디서 많이 쓰이나"를 정리하다가, `browse()`가
그 날짜의 이벤트를 개수 제한 없이 전부 돌려준다는 걸 다시 짚게 됐다. 코퍼스에서
이벤트가 제일 많은 날(2026-07-27, 2,844개)로 실제 프롬프트 크기를 재봤다.

```python
events = browse('2026-07-27')          # 2,844개
total = sum(min(len(e['text']), 300) + 60 for e in events)
# -> 1,005,356자
```

하루 요약 하나가 100만 자를 넘었다. "정리해줘"/"비교해줘" 류 질문에 이런 날짜가
섞이면(예: "최근 3일") 그대로 재현된다 — 지금까지는 우연히 이벤트가 적은 날들로만
테스트해서 안 걸렸을 뿐이다.

**Action**
`config.py`에 `MAX_EVENTS_PER_DAY_SUMMARY = 60`을 추가하고, `summarize.py`에
`_thin_out()`을 만들어 `summarize_day()`가 `browse()` 직후 적용하게 했다.

앞에서부터 60개만 자르는 대신 **일정한 간격으로 골라냈다**:
```python
step = len(events) / max_events
return [events[int(i * step)] for i in range(max_events)]
```
앞에서부터 자르면 하루의 오전 몇 시간만 남고 오후·저녁이 통째로 사라진다.
간격을 두고 뽑으면 개수는 줄어도 하루 전체 흐름은 유지된다.

**Result**
LLM 호출 없이 로컬에서 검증했다(크레딧 소진 상태였기 때문이기도 하다).

| | 수정 전 | 수정 후 |
|---|---|---|
| 이벤트 개수 | 2,844 | **60** |
| 프롬프트 크기 | 1,005,356자 | **22,730자 (−97.7%)** |

솎아낸 60개의 시간대를 확인하니 08:38(오전) / 14:09(오후) / 17:52(저녁)로
하루 전체에 걸쳐 남아있었다 — 단순 앞자르기였다면 전부 오전에 몰렸을 것이다.

> `ask()`에서 이미 한 번 겪은 문제(근거 하나당 글자 상한 없음, 3번 항목)와
> 같은 종류의 버그가 다른 함수(`summarize_day()`)에서 또 났다. **"이 함수가
> 외부 데이터를 개수/크기 제한 없이 그대로 프롬프트에 넣는가"는 새 함수를
> 만들 때마다 매번 따로 확인해야 한다** — 한 번 고쳤다고 프로젝트 전체에
> 자동으로 적용되지 않는다.
