# 트러블슈팅 기록 (STAR)

화면 기록 RAG를 만들면서 겪은 문제와 해결 과정. 숫자는 전부 실행 로그에서 그대로 가져왔다.

---

## 1. 프레임 중복으로 검색이 무의미해지는 문제

**Situation**
screenpipe는 3~6초 간격으로 화면을 캡처하는데, 화면이 안 바뀌는 동안에는
프레임마다 텍스트가 사실상 동일하다. 프레임 1개를 문서 1개로 그대로 색인했더니
무엇을 검색해도 가장 자주 반복되는 텍스트(사이드바 메뉴 등)가 상위에 잡혔다.
검색 결과에 "Collapse sidebar / 검색 / 홈" 같은 UI 요소만 계속 보이는 상태였다.

원본 규모는 하루치(2026-07-28) 기준 프레임 2,905개 / 20,251,452자였다.

**Task**
프레임이 아니라 "하나의 활동"을 검색 단위로 만들어야 했다. 다만 다음 두 가지를
동시에 만족해야 했다.
- 단순히 이어붙이면 글자 수가 전혀 줄지 않는다 (문서만 거대해짐)
- 앱 단위로 통째로 합치면 "언제 있었던 일인지"가 뭉개진다

**Action**
- 앱+창이 같은 **연속** 프레임만 하나의 그룹으로 묶었다. 시간이 떨어진 동일 앱은
  별도 그룹으로 둬서 시각 정보가 뭉개지지 않게 했다.
- 그룹 안에서 이미 등장한 줄을 `seen` 집합으로 추적해 중복 줄만 제거했다.
- 창 제목이 안 바뀌는 앱(Claude, Code)에서 서로 다른 작업이 한 덩어리가 되는 문제가
  있어, 그룹 안에서도 다음 조건이면 이벤트를 끊게 했다.
  - 연속 프레임 간 자카드 유사도(`overlap`)가 0.3 미만 — 화면이 통째로 바뀜
  - 누적 글자 수가 2,000자 초과 — 긴 세션이 계속 불어남
- 끊는 지점은 글자 중간이 아니라 **프레임 경계**로 잡아, 각 이벤트가 실제 프레임
  구간에 대응하도록 했다.

**핵심 시행착오 — `seen`을 언제 비우는가**

이벤트를 끊을 때 `seen`도 같이 초기화했더니 글자 수가 오히려 폭증했다.
화면 텍스트는 앞부분이 그대로 유지되면서 몇 줄만 늘어나는(prefix-growing) 구조라,
`seen`을 비우는 순간 다음 이벤트가 이미 내보낸 수천 자를 통째로 다시 담았다.

| `seen` 스코프 | 총 글자 |
|---|---|
| 이벤트마다 초기화 | 3,045,016자 |
| **그룹 전체에서 유지** | **821,501자** |

**4배 차이**였다. 이벤트를 끊는 것은 *자르는 위치*만 정하는 것이고,
*중복 제거 기억*은 그룹 내내 유지되어야 한다는 걸 여기서 확인했다.

> 중복 제거 로직에서는 "무엇을 제거하는가"보다
> **"제거 기억을 언제 버리는가"** 가 더 민감하다.

**Result**
하루치(2026-07-28) 기준 프레임 2,905개 / 20,251,452자 → 이벤트 1,303개 /
4,358,293자로 **약 79% 감소**. 실제 색인 시점에는 캡처가 계속 진행 중이어서
1,313개 이벤트로 저장됐다.

무작위 표본을 직접 읽었을 때 "이때 이거 했지"가 읽히는지로 정성 검증도 통과했다.

## 2. 전량 재임베딩으로 실험 자체가 불가능해지는 문제

**Situation**
색인 대상을 하루(2026-07-28)에서 전체 7일(2026-07-22~28)로 늘리는 시점이었다.
하루치 색인만으로도 이벤트 1,313개(4.36M자) 임베딩에 **12분 50초**가 걸렸다.
7일이면 1시간을 훌쩍 넘기는데, 문제는 시간 자체가 아니라 다음 두 가지였다.

- 중간에 실패하면 그때까지 임베딩한 게 전부 날아간다
- 정제 파라미터를 조금만 바꿔도 전체를 다시 태워야 해서, 하루에 여러 번
  재실험하는 게 불가능해진다

임베딩 배치 크기도 제약이었다. 기본값(32)으로 돌리면 화면 텍스트가 길어서
MPS 메모리가 터졌고, `EMBED_BATCH_SIZE=4`로 낮춘 대가가 이 소요 시간이었다.

**Task**
날짜가 늘어나도 이미 색인된 날짜는 다시 임베딩하지 않고, 중간에 실패해도
그 이전 날짜 결과는 보존되는 색인 방식이 필요했다.

**Action**
- **색인 단위를 하루로 쪼갰다.** `index_date(date)`를 최소 단위로 두고,
  하루가 끝날 때마다 즉시 chroma에 저장하게 했다.
- **이벤트 id를 내용 해시로 만들었다.** `app + window + start + text`를 SHA1로
  해싱해서, 같은 이벤트는 몇 번을 재실행해도 같은 id가 나오도록 했다.
  순번(0, 1, 2...)을 쓰면 실행할 때마다 id가 달라져서 재시도가 곧 중복 생성이 된다.
- **`insert` 대신 `upsert`를 썼다.** 위의 멱등 id와 짝을 이루는 선택으로,
  재실행 시 에러 없이 덮어쓰기가 된다.
- **이미 색인된 날짜를 조회해 건너뛰게 했다.** `indexed_dates()`가 chroma
  metadata의 `date` 필드를 확인하고, `index_all()`은 없는 날짜만 순서대로 처리한다.

**Result**
07-22~07-27 배치 실행 로그:

| 날짜 | 이벤트 수 |
|---|---|
| 07-22 | 1,009 |
| 07-23 | 1,533 |
| 07-24 | 2,021 |
| 07-25 | 74 |
| 07-26 | 18 |
| 07-27 | 2,844 |
| 07-28 | 건너뜀 - 이미 있음 |

전체 8,812개 이벤트 누적. 이미 색인돼 있던 07-28을 재임베딩 없이 정확히 건너뛰는
것을 실행 로그로 확인해, 멱등성 설계가 실제로 동작함을 검증했다.

부수적으로 07-25(74개), 07-26(18개)은 다른 날의 1/20~1/100 수준이었는데,
원본 프레임을 확인해보니 각각 106개 / 21개로 캡처 자체가 적었다.
정제 로직 문제가 아니라 그 기간에 screenpipe가 거의 안 돌았던 것으로,
데이터 이상을 정제 버그로 오인하지 않도록 원본까지 되짚어 확인했다.

## 3. 프롬프트 크기가 제어되지 않아 LLM 토큰 비용이 튀는 문제

**Situation**
평가 세트(15문항)를 돌린 뒤 LLM API 사용량이 예상보다 크게 늘었다.
호출 횟수 자체는 17번(테스트 2 + 평가 15)으로 많지 않았기 때문에,
호출당 프롬프트 크기를 의심하고 실측했다.

색인된 이벤트 8,812개의 크기 분포는 다음과 같았다.

| | 글자 수 |
|---|---|
| 중앙값 | 1,270 |
| 평균 | 1,848 |
| 상위 10% | 3,485 |
| **최대** | **36,870** |

중앙값과 최대값이 **29배** 차이 났다. 정제 단계에서 이벤트를 끊는 기준
(`MAX_EVENT_CHARS=2000`)은 프레임 경계에서만 검사하기 때문에, 프레임 하나가
통째로 크면 그 이벤트는 상한을 크게 초과한 채로 만들어진다.

**Task**
`build_context()`가 검색 결과 `k=5`개의 본문을 **아무 제한 없이** 프롬프트에
그대로 넣고 있었다. 큰 이벤트가 우연히 몇 개 걸리는 것만으로 프롬프트가 수십 배로
부푸는 구조라, 비용이 질문 내용에 따라 예측 불가능하게 튀었다.
이론상 최악은 36,870자 × 5 = 약 18만 자였다.

**Action**
- `CONTEXT_CHARS_PER_HIT = 1500`을 설정에 추가하고, `build_context()`에서
  근거 하나당 글자 수를 잘라내도록 했다. 잘린 경우 `…(잘림)` 표시를 붙여
  LLM이 뒷부분이 생략됐음을 알 수 있게 했다.
- 상한값은 이벤트 크기 분포에서 정했다. 중앙값(1,270자)보다는 크게 잡아
  대부분의 이벤트는 손실 없이 통과시키고, 상위 10%(3,485자) 이상의
  비정상적으로 큰 이벤트만 잘리도록 1,500자로 뒀다.
- 검증은 **LLM 호출 없이** 했다. 임베딩은 로컬(bge-m3)이므로 `search()`로
  실제 검색만 수행하고 `build_context()` 결과 길이만 재서, 비용 조사 과정에서
  추가 비용이 발생하지 않게 했다.

**Result**
실제 평가 세트 15문항, k=5 기준 측정값:

| | 수정 전 | 수정 후 |
|---|---|---|
| 합계 | 228,970자 | **95,693자 (−59%)** |
| 질문당 평균 | 15,264자 | **6,379자** |
| **최대 (단일 질문)** | 46,129자 | **7,846자** |

평균이 절반 이하로 줄어든 것보다, **최대값이 46,129자에서 7,846자로 묶인 것**이
핵심이다. 비용의 상한이 질문 내용과 무관하게 `k × 1500자`로 고정되면서,
"어떤 질문이 걸리느냐"에 따라 비용이 튀는 문제가 사라졌다.

부수적으로 얻은 교훈: **임베딩(로컬)과 LLM 호출(API)의 비용 구조가 완전히 다르다.**
13분씩 걸린 색인 작업은 API 비용이 0이었고, 몇 초 만에 끝나는 질의 응답이
실제 비용의 전부였다. 소요 시간과 비용이 반비례하는 구조라, 체감으로
비용을 짐작하면 틀린다.

## 4. 라우팅 LLM이 없는 앱을 지어내는 문제

**Situation**
`router.py`에 hybrid 라우팅(규칙 우선, 실패 시 LLM 폴백)을 추가한 뒤, "LLM 호출이
너무 잦아지는 거 아니냐"는 우려가 있었다. 실제 빈도를 확인하려고 `router.py`에
카운터(`get_stats()`)를 추가하고, 사전에 없는 표현 3개(q16~q18: "화상회의 앱",
"파일 관리자", "쉘")를 질문 세트에 넣어 `eval/eval_routing.py`로 라우팅만
(생성 없이) 18문항을 돌렸다.

**Task**
호출 빈도를 재는 게 목적이었는데, 결과표를 읽다가 다른 문제가 먼저 보였다.
app 일치가 14/18로, 새로 추가한 3문항이 아니라 **기존에 이미 성공하던 4문항**
(q11, q12, q14, q15)에서 실패가 나왔다. 전부 앱 이름을 전혀 언급 안 한 순수
내용 질문(semantic/keyword 카테고리)이었다.

**Action**
직접 `route()`를 호출해 원인을 확인했다.

```
"RAG 파이프라인 설계에 대해 무슨 얘기를 했어?" -> {"app": "Code", ...}
"임베딩 모델이나 벡터 검색에 대해 뭘 찾아봤어?" -> {"app": "Google Chrome", ...}
"chromadb에 대한 내용을 찾아줘"              -> {"app": "Google Chrome", ...}
"screenpipe에 대해 뭘 알아봤어?"              -> {"app": "Google Chrome", ...}
```

규칙이 app/hour/date를 하나도 못 찾으면 무조건 LLM에게 넘기는데, LLM이 "이런
내용이면 아마 이 앱에 있겠지"라고 **없는 정보를 추측**했다. 원래 프롬프트가
"app: 다음 중 하나 또는 null"이라고만 돼 있어서, null을 골라도 되는 상황을
구체적으로 알려주지 않았다.

이 4문항은 필터 없이 이미 100% 성공하던 질문들이다. 그대로 라우팅에 연결했으면
잘 되던 검색을 라우팅이 오히려 망가뜨릴 뻔했다 — 호출 빈도를 재려던 카운터가
비용 문제보다 먼저 정확도 버그를 잡아낸 것이다.

`LLM_PROMPT`에 조건을 명시적으로 추가했다.

```
app: 다음 중 하나 또는 null - {apps}
    질문이 특정 앱이나 앱 종류(에디터, 메신저, 화상회의 등)를 가리킬 때만 채운다.
    "~에 대해 뭘 찾아봤어", "~얘기했어"처럼 내용을 묻는 질문은 앱을 추측하지 말고 null로 둔다.
```

**Result**

| | 수정 전 | 수정 후 |
|---|---|---|
| app 일치 | 14/18 | **17/18** |

q11, q12, q15는 정확히 null로 고쳐졌다. **q14("chromadb")만 여전히 Google Chrome을
지어낸다** — "chromadb"라는 글자가 "Chrome"과 형태적으로 겹쳐서, 지시문을 줘도
그 착각을 못 이긴다. 미해결로 남겨뒀다. 개선 후보로 "결론(JSON)부터 내지 말고
판단 근거를 먼저 글로 쓰게 한 뒤 JSON을 내게 하는" reasoning 방식을 검토했으나
아직 적용하지 않았다.

애초에 재려던 호출 빈도(9/18, 50%)는 이번 수정으로 줄지 않았다 — "규칙이
못 찾았다"는 것이 "필터가 있는데 규칙이 놓쳤다"와 "애초에 필터가 필요 없는
질문이다"를 구분 못 하기 때문이다. 다만 라우팅 LLM 호출 하나가 284자로 생성
호출 평균(6,379자)의 1/22 수준이라, 빈도가 높아도 당장 손해는 크지 않다고 보고
`get_stats()`로 실사용 빈도만 지켜보기로 하고 넘어갔다.

> 카운터를 달아서 재려던 것과 실제로 발견한 문제가 달랐다. 비용을 재려다
> 정확도 버그를 먼저 잡았다 — 뭘 재려고 계측을 붙이든, 계측 결과 자체를
> 있는 그대로 읽어보는 게 항상 남는다.

## 5. 하루 요약 프롬프트가 이벤트 개수 상한 없이 100만 자를 넘는 문제

**Situation**
4단계(여러 날짜 조회)를 만들면서 `summarize_day()`가 `browse()`로 그 날짜의
이벤트를 전부 가져와 프롬프트에 넣게 짰다. `ask()`(단일 날짜 검색)엔 이미
`CONTEXT_CHARS_PER_HIT`로 이벤트 하나당 글자 상한이 있었지만, `summarize_day()`엔
**이벤트 몇 개까지 넣을지에 대한 상한이 아예 없었다.**

**Task**
"LLM 호출은 어디서 일어나고 토큰은 어디서 많이 쓰이나"를 정리하다가, `browse()`가
그 날짜의 이벤트를 개수 제한 없이 전부 돌려준다는 걸 다시 짚게 됐다. 코퍼스에서
이벤트가 제일 많은 날(2026-07-27, 2,844개)로 실제 프롬프트 크기를 재봤다.

```python
events = browse('2026-07-27')          # 2,844개
total = sum(min(len(e['text']), 300) + 60 for e in events)
# -> 1,005,356자
```

하루 요약 하나가 100만 자를 넘었다. "정리해줘"/"비교해줘" 류 질문에 이런 날짜가
섞이면(예: "최근 3일") 그대로 재현된다 — 지금까지는 우연히 이벤트가 적은 날들로만
테스트해서 안 걸렸을 뿐이다.

**Action**
`config.py`에 `MAX_EVENTS_PER_DAY_SUMMARY = 60`을 추가하고, `summarize.py`에
`_thin_out()`을 만들어 `summarize_day()`가 `browse()` 직후 적용하게 했다.

앞에서부터 60개만 자르는 대신 **일정한 간격으로 골라냈다**:
```python
step = len(events) / max_events
return [events[int(i * step)] for i in range(max_events)]
```
앞에서부터 자르면 하루의 오전 몇 시간만 남고 오후·저녁이 통째로 사라진다.
간격을 두고 뽑으면 개수는 줄어도 하루 전체 흐름은 유지된다.

**Result**
LLM 호출 없이 로컬에서 검증했다(크레딧 소진 상태였기 때문이기도 하다).

| | 수정 전 | 수정 후 |
|---|---|---|
| 이벤트 개수 | 2,844 | **60** |
| 프롬프트 크기 | 1,005,356자 | **22,730자 (−97.7%)** |

솎아낸 60개의 시간대를 확인하니 08:38(오전) / 14:09(오후) / 17:52(저녁)로
하루 전체에 걸쳐 남아있었다 — 단순 앞자르기였다면 전부 오전에 몰렸을 것이다.

> `ask()`에서 이미 한 번 겪은 문제(근거 하나당 글자 상한 없음, 3번 항목)와
> 같은 종류의 버그가 다른 함수(`summarize_day()`)에서 또 났다. **"이 함수가
> 외부 데이터를 개수/크기 제한 없이 그대로 프롬프트에 넣는가"는 새 함수를
> 만들 때마다 매번 따로 확인해야 한다** — 한 번 고쳤다고 프로젝트 전체에
> 자동으로 적용되지 않는다.

## 6. 사용자 리포트("dates=None") 재현 시도 — 코드가 아니라 실행 환경 문제였음

**Situation**
사용자가 대화형 세션에서 `"지난주 카톡내용 비교해줘"`를 물었더니
`dates=None intent=None`이 나와 필터 없이 엉뚱하게 답했다고 보고했다. 같은
"지난주"가 들어간 다른 세 질문은 정상 작동했다는 것도 같이 보고됐다.

**Task**
버그인지, 버그라면 어디서 나는지 확인해야 했다. 코드를 고치기 전에 재현부터
해야 헛수고를 안 한다.

**Action**
`find_date_range()` 단독 호출, 그리고 `route()` 전체 호출(hybrid 모드) 두
방식으로 정확히 같은 문자열을 두 번 넣어봤다.

```python
find_date_range("지난주 카톡내용 비교해줘", today)  # -> 7일치 정상 반환
route("지난주 카톡내용 비교해줘", mode="hybrid")     # -> dates/intent 정상 반환
```

**Result**
**재현되지 않았다.** 코드는 두 경로 모두에서 정상 작동했다. 유력한 원인은
사용자가 `uv run python -m screenlog.ask` 대화형 세션을 켜둔 채 계속
질문만 입력했을 가능성 — 파이썬은 실행 중인 프로세스에 파일 수정을 자동
반영하지 않으므로, 그 세션이 최근 수정 이전 코드로 돌고 있었을 수 있다.

> "재현이 안 된다"는 것도 유효한 조사 결과다. 코드를 괜히 더 고치는 대신
> "코드 문제가 아니라 실행 환경(낡은 프로세스) 문제일 가능성이 높다"고
> 결론 내리고, 사용자에게 프로세스 재시작 후 재확인을 안내했다. 재현 안
> 되는 버그를 붙잡고 코드를 계속 고치는 게 더 위험할 수 있다 — 있지도
> 않은 원인을 찾다가 진짜 코드에 문제를 만들 수 있기 때문이다.

## 7. LLM 라우팅의 근본 문제 — 응답을 사후 검증하지 말고 애초에 강제해야 했다

**Situation**
`route_llm()`이 "JSON만 출력해라"라고 텍스트로 부탁하고, 응답에서 정규식으로
`{...}` 부분을 찾아 파싱한 뒤, `app not in APP_ALIASES`처럼 사후에 걸러내는
방식이었다(4번 항목에서 프롬프트 지시로 완화했던 그 코드). "chromadb에 대한
내용을 찾아줘"가 같은 프롬프트로 한 번은 `Google Chrome`을 지어내고 한 번은
`null`을 정확히 반환하는 등, **같은 입력에 다른 결과**가 나오는 게 근본적으로
남아있었다.

**Task**
사후 검증이 아니라, LLM이 애초에 정해진 형식·정해진 값만 낼 수 있게 API
레벨에서 강제하는 방법이 있는지 확인하고, 되면 적용한다.

**Action**
게이트웨이가 OpenAI 호환 `response_format`을 지원하는지 먼저 최소 비용으로
확인했다.

```python
response_format={"type": "json_object"}                    # 지원됨
response_format={"type": "json_schema", "json_schema": {...,"strict": True}}  # 지원됨
```

`json_schema` strict 모드에서 `app` 필드를 `enum: [...APP_ALIASES.keys(), None]`으로
제한했다. `route_llm()`을 다시 짜서 정규식 추출·`json.JSONDecodeError` 방어·
`app not in APP_ALIASES` 사후 검사를 걷어냈다 — 스키마가 애초에 그 값만
내보낼 수 있게 막아주므로 필요 없어졌다.

**부수적으로 발견한 새 버그**: 재검증하려고 18문항 라우팅 평가를 돌렸더니
`app`은 18/18인데 `date`가 3개 틀렸다. 둘로 갈렸다:
- q06/q09는 실제로는 정답이었다. `eval_routing.py`가 `expect_date_offset`
  (5번 항목 이전에 추가한, 상대 날짜를 실행 시점 기준으로 계산하는 로직)을
  안 쓰고 있어서 낡은 값과 비교해 가짜로 틀린 것처럼 보였다.
- q18("쉘에서 무슨 명령을 실행했어?")은 **진짜 버그**였다. 새로 쓴 프롬프트가
  `app`엔 "추측하지 말고 null로 둔다"를 넣었는데 `hour`/`date`엔 똑같은 지시를
  안 넣어서, 날짜 언급이 전혀 없는 질문에 `route_llm()`이 오늘 날짜를
  지어냈다.

두 개 다 고쳤다 — 프롬프트에 세 필드 전부 "언급됐을 때만 채우고 없으면 null"을
명시했고, `eval_routing.py`가 `run_eval.py`의 `resolve_expect_date`를 재사용하게
했다(같은 로직을 두 번 짜지 않도록).

**Result**

| | 이전 | 이후 |
|---|---|---|
| app 정확도(18문항) | 15/18(chromadb 불안정) | **18/18** |
| date 정확도(18문항) | 15/18(q18 회귀 포함) | **18/18** |
| chromadb → Chrome 오인식 | 간헐적 재현 | 재현 안 됨(enum으로 구조적 차단) |

> 재검증하려고 돌린 평가가 고치려던 문제(app 안정성)와 무관한 새 버그(date
> null 지시 누락)를 잡아냈다. **한 필드에 넣은 안전장치를 다른 필드에도
> 똑같이 넣었는지는 자동으로 안 따라온다** — 프롬프트를 고칠 때마다 모든
> 필드를 같은 기준으로 다시 훑어야 한다. 4번 항목의 교훈("한 곳을 고쳤다고
> 전체가 안전해지지 않는다")이 필드 단위에서도 그대로 반복됐다.

## 8. 재귀 오염(recursive contamination) 재현 — 미해결로 남김

**Situation**
"어제 뭐배웠어?" 질문에 근거 5개가 전부 정확히 07-28로 필터링됐는데도,
답변은 07-27 오후 3시 23분~5시 9분이라는, 근거 어디에도 없는 시간대를
인용했다. 처음엔 LLM이 날짜를 잘못 계산한 걸로 의심했다.

**Task**
근거의 실제 텍스트 본문까지 확인해서 진짜 원인을 찾는다.

**Action**
`search()`로 그 5개 근거의 `text` 원문을 직접 열어봤다. 2026-07-28T11:47:03
Claude 화면 캡처 안에, 예전에 `screen-agent` 프로젝트의 `_summarize_day()`를
디버깅하며 화면에 출력했던 **예시 결과물**이 그대로 찍혀 있었다.

```
=== LLM이 쓴 07-27 요약 원문 ===
[2026-07-27]
2026-07-27 오후 3시 23분부터 5시 9분까지, 사용자는 Zoom 회의에 참여하여...
```

**Result**
LLM은 근거를 정확히 인용했다 — 문제는 그 근거 자체가 실제 활동이 아니라
**AI가 화면에 출력한 디버깅 예시 텍스트**였다는 것. 검색·라우팅·프롬프트
전부 정상 작동했는데도 답이 틀렸다.

**미해결로 남긴다.** 이건 이번에 새로 발견한 게 아니라, 전작 `screen-agent`의
`REPORT_details.md`에 "재귀 오염"이라는 이름으로 이미 기록돼 있던, 화면 기록
RAG 고유의 구조적 함정이 그대로 재현된 것이다 — "faithfulness로는 절대
안 잡힌다. 근거 문서에 진짜 그렇게 쓰여 있으니 만점이 나온다"는 그때 결론이
이번에도 그대로 맞았다. 대응책 후보(AI 앱 제외 / 입력 영역만 보존 /
신뢰도 플래그)도 그때와 같은 채로 미착수 상태다.

> 같은 이름의 문제가 다른 프로젝트에서 그대로 재현됐다는 것 자체가 증거다 —
> **화면 기록을 다루는 RAG는 "AI 도구 사용 중 화면"을 코퍼스에서 특별
> 취급하지 않으면 이 함정을 피할 수 없다.** 임시방편이 아니라 설계
> 단계에서 결정해야 하는 문제로 남겨둔다.

## 9. 색인이 20분에서 몇 시간으로 느려진 문제 — 원인이 4겹으로 쌓여 있었다

**Situation**
평소 20분이면 끝나던 하루치 색인(`uv run python -m screenlog.index`)이
갑자기 배치 1개(이벤트 4개)당 123초씩 걸렸다. `tqdm`이 계산한 전체 예상
시간은 21시간 45분. 처음엔 "데이터가 많아져서 그런가" 의심했다.

**Task**
"오늘따라 느리다"는 증상 하나에 원인 후보가 여러 개(데이터량, GPU,
메모리, 프로세스) 걸쳐 있어서, 하나씩 지우면서 진짜 원인을 좁혀야 했다.
가설을 세우면 바로 수치로 반증하거나 확인하는 순서로 진행했다.

**Action**

1. **"데이터가 늘었다"는 가설을 먼저 지웠다.** chromadb에 저장된 날짜별
   이벤트 수를 직접 조회해보니, 문제가 된 날(2,539개)보다 이미 정상적으로
   색인됐던 다른 날(2,844개)이 더 많았다. 데이터량은 범인이 아니었다.

   ```
   2026-07-24  2021개
   2026-07-27  2844개   ← 문제 없이 색인됐던 날 (오늘보다 많음)
   2026-07-29  2539개   ← 지금 123초/배치가 나는 날
   ```

2. **"GPU(MPS)를 안 쓰나?" 가설을 세우고 직접 벤치마크했다.**
   `torch.backends.mps.is_available()`은 `True`, 모델을 실제로 로드해서
   같은 길이(2,000자)의 텍스트를 인코딩해보니 배치당 0.6~3초 — 정상.
   MPS 자체는 문제가 아니었다. **격리된 벤치마크로 재현이 안 되면, 문제는
   코드가 아니라 "그 순간의 실행 환경"에 있다는 뜻**이다(6번 항목과 같은
   결론 구조).

3. **`ps aux` + `sysctl vm.swapusage`로 시스템 자원을 봤다.** 스왑이
   23.2GB/24.5GB로 거의 꽉 차 있었고, Docker Desktop의 리눅스 VM이 8GB를
   상시 예약(`--memoryMiB 8192`)하고 있었다. VM을 내리자 배치당
   123초 → 16초로 **8배** 개선됐다.

4. **그래도 벤치마크(0.6~3초)보다 5~10배 느렸다.** `ps aux`를 다시 보니
   `screenlog.index` 프로세스가 세 개나 떠 있었다 — 전부 상태가 `T`(정지).
   Ctrl+C로 안 죽어서 급한 마음에 Ctrl+Z를 눌렀던 흔적이었다.
   **SIGINT(Ctrl+C)는 "종료 요청"이라 파이썬 바이트코드 경계에서만
   처리되는데, `model.encode()` 실행 중엔 실행이 torch의 네이티브(C++)
   코드 안에 있어서 신호를 못 받는다.** 반응이 없어 보여서 Ctrl+Z를
   눌렀는데, 그건 SIGTSTP(일시정지)라 프로세스가 안 죽고 모델을 문 채
   백그라운드에 얼어붙는다. `kill -9`로 전부 정리하자 스왑이 다시
   빠지기 시작했다.

5. **정리 후에도 물리 메모리 자체가 16GB였다.** Activity Monitor로 확인한
   메모리 압력 그래프에 빨간 구간이 반복해서 찍혀 있었고, VS Code 확장
   프로세스(`Code Helper (Plugin)`)만 여러 개가 각각 수백 MB씩, 안 쓰는
   `mysqld`, Spotlight(`mds_stores`)까지 겹쳐서 16GB를 상시 소진하고
   있었다. bge-m3(568M 파라미터) 로딩만으로 수 GB가 필요한 상황에서는
   이 정도 배경 부하도 스왑 발생 임계점을 넘기기에 충분했다.

**Result**
원인은 하나가 아니라 **네 겹으로 쌓여 있었다** — ① Docker Desktop VM의
상시 메모리 예약(8GB) ② Ctrl+Z로 방치된 좀비 프로세스(모델 중복 로딩)
③ VS Code/Spotlight 등 배경 프로세스의 메모리 점유 ④ 16GB라는 물리
메모리 자체의 한계. 이 중 어느 하나만 봤으면 "왜 여전히 느리지"에서
막혔을 것이다. 조치 후 배치당 시간은 여전히 부하 상황에 따라 흔들렸지만
(16초~50초대), 최소 8배 이상 개선됐고 원인이 실행 환경이라는 것도
데이터로 확인됐다.

부수적으로 발견한 설계 결함도 하나 있다: `index_date()`는 하루치
이벤트를 **전부 임베딩한 뒤에야** chromadb에 한 번에 저장한다
([index.py:88-100](../src/screenlog/index.py)). 즉 몇 시간을 계산해도
중간에 프로세스가 죽으면 그 하루치 진행분이 통째로 날아간다 — 느린
환경일수록 이 리스크가 커지는 구조라, 배치 단위 저장으로 바꾸는 게
다음 개선 항목이다.

> 증상 하나("느리다")에 원인을 하나로 단정하지 않고, 매 단계마다
> **가설을 수치로 반증 가능하게 만들어 지워나간 것**이 핵심이었다.
> "데이터가 늘었나?"는 DB 쿼리로, "GPU 문제인가?"는 격리된 벤치마크로,
> "메모리 문제인가?"는 `ps`/`vm_stat`/Activity Monitor로 — 전부 말이
> 아니라 숫자로 확인하고 나서야 다음 원인으로 넘어갔다.

## 10. `torch.mps.empty_cache()` 안 부르면 색인이 진행할수록 메모리를 15GB까지 먹는다

**Situation**
9번 항목에서 발견한 설계 결함(하루치를 전부 임베딩한 뒤에야 한 번에
저장하는 구조)을 고치려고 `index_date()`를 청크(200개) 단위로 임베딩 ->
즉시 저장 -> 재실행 시 이어서 하는 구조로 바꿨다. 그런데 고친 코드로
7/28을 다시 돌리자 1,200개(청크 6개)쯤 지나면서 배치 하나가 26초, 48초로
느려지기 시작했고, `top`으로 보니 색인 프로세스가 메모리 15GB를 먹은 채
`stuck` 상태였다.

**Task**
"데이터량 문제가 아니다"는 이미 9번 항목에서 확인했고 Docker VM이나 좀비
프로세스도 이번엔 없었다. 그렇다면 남은 후보는 방금 바꾼 코드 자체 —
청크마다 `embed()`를 반복 호출하는 구조가 뭔가를 누적시키고 있는지를
격리된 벤치마크로 확인해야 했다.

**Action**
1. **`top -o mem`으로 범인 프로세스를 먼저 특정했다.** 색인 프로세스
   (PID 65123)가 15GB, `stuck` 상태 — 배경 프로세스가 아니라 색인
   자체가 원인이라는 게 바로 나왔다.
2. **실제 7/28 데이터로 `embed()`를 반복 호출하며 MPS 메모리를
   추적했다.** `torch.mps.driver_allocated_memory()`(캐시 풀 전체)와
   `torch.mps.current_allocated_memory()`(실제 사용 중인 양)를 배치마다
   찍어봤다.
   ```
   배치   0  MPS driver 3,042MB   (배치 최대길이 10,260자)
   배치  44  MPS driver 5,090MB   (배치 최대길이 10,159자)
   배치 100  MPS driver 8,163MB   (배치 최대길이 14,914자)
   배치 140  MPS driver 9,699MB   (배치 최대길이 36,870자 ← 최댓값)
   ```
   `current_allocated_memory`(실사용량)는 2,165MB로 끝까지 고정인데
   `driver_allocated_memory`(캐시 풀)만 계속 불어났다. **원인이 코드가
   아니라 데이터인지 프레임워크인지를 가르는 신호는 "실사용량은 그대로인데
   캐시만 커진다"였다** — 메모리 누수가 아니라 캐시 반납 누락이라는 뜻.
3. **원인을 특정했다.** 화면 텍스트 길이가 100~36,870자로 매우
   불균일한데, PyTorch의 MPS 캐싱 할당자는 배치마다 시퀀스 길이가 달라질
   때마다 그 크기의 새 메모리 블록을 캐시에 쌓기만 하고 재사용하거나
   반납하지 않는다(CUDA 쪽엔 있는 스마트한 블록 재사용이 MPS엔 약하다).
   이벤트 200개(배치 50개)만 처리해도 캐시가 3GB→9.7GB로 불어났으니,
   하루치(2,383개, 배치 596개)를 다 돌면 물리 메모리를 다 먹고도 남는
   양이었다.
4. **`embed()` 끝에 `torch.mps.empty_cache()`를 추가하고 같은
   벤치마크로 재검증했다.** 이벤트 400개(배치 100개, 36,870자짜리 배치
   포함)를 다 돌려도 `driver_allocated_memory`가 3,034.6MB에서 **1바이트도
   안 늘고** 끝까지 고정됐다.

**Result**
`embed()`가 배치를 만들 때마다 `torch.mps.empty_cache()`를 호출하도록
[index.py:34-46](../src/screenlog/index.py)를 고쳤다. 원래도 있었던 문제인데
(한 번에 전체를 `encode()`했던 예전 코드에서도 캐시는 똑같이 불어났을 것이다)
스왑 여유가 있는 날은 안 터지고 여유가 없는 날(9번 항목의 7/29)만 터져서
"환경 문제"로만 보였던 것 — 이번에 청크 단위로 쪼개면서 진행 상황을 자주
찍어보게 됐고, 그 덕에 "캐시가 계속 커진다"는 패턴이 눈에 보여서 근본
원인까지 잡을 수 있었다.

> 메모리가 늘어나는 증상을 볼 때 **"실제로 쓰는 양"과 "프레임워크가 쥐고
> 있는 양"을 분리해서 재는 것**이 핵심이었다. 둘 다 같이 늘면 진짜 누수
> (데이터가 어딘가에 계속 쌓임)를 의심해야 하지만, 실사용량은 그대로인데
> 캐시만 커진다면 반납 누락이고, 해당 프레임워크의 캐싱 할당자 문서를
> 찾아보면 대개 `empty_cache()` 같은 탈출구가 있다.

## 11. 대시보드 첫 로딩이 데이터가 쌓일수록 느려지는 문제

**Situation**
대시보드에 처음 접속할 때 데이터가 올라오는 속도가 느리다는 사용자 보고가
있었다. `db.sqlite`가 890MB(18,616개 이벤트)까지 커진 시점이었다.

**Task**
"느리다"는 증상 하나였지만, 대시보드 로딩 경로에 걸리는 함수가
`get_collection()`(연결) → `build_stats()`(집계) 두 단계라 각 단계를
따로 떼어 시간을 재야 어디가 병목인지 알 수 있었다.

**Action**
`time`으로 단계별 소요 시간을 직접 쟀다.

```python
t0 = time.time()
col = get_collection()
t1 = time.time()   # PersistentClient 연결: 4.25초

metas = col.get(include=['metadatas'])['metadatas']
t2 = time.time()   # 전체 metadata(18,616개) 조회: 2.28초
```

원인은 [index.py:52-58](../src/screenlog/index.py)의 `get_collection()`이
호출될 때마다 `chromadb.PersistentClient(path=CHROMA_DIR)`로 **매번 클라이언트를
새로 열고 있었다**는 것. 같은 파일의 `get_model()`([index.py:27-33](../src/screenlog/index.py))은
전역 변수(`_model`)에 캐시해서 한 번만 로드하는데, `get_collection()`은 그 패턴을
따르지 않고 있었다. `db.sqlite`가 커질수록 매번 여는 비용이 그대로 누적된다.

`get_model()`과 동일한 패턴(모듈 전역 `_collection` 캐시)으로 고쳤다.

**Result**

| | 캐싱 전 | 캐싱 후 |
|---|---|---|
| 첫 호출 | 4.25초 | (프로세스 시작 후 1회만 발생) |
| 이후 호출 | 4.25초(매번) | **0.000초** |

서버(uvicorn) 프로세스가 살아있는 동안 클라이언트를 한 번만 열고 재사용하므로,
서버를 껐다 켜지 않는 한 이 비용을 다시 치르지 않는다.

**미해결로 남긴 것**: `stats.py`의 `build_stats()`는 여전히 매 요청마다
전체 이벤트 metadata를 캐시 없이 다시 훑어서 집계한다([stats.py:87-90](../src/screenlog/stats.py)).
지금은 집계 자체가 0.5초 수준으로 빠르지만, 이벤트 수가 계속 늘어나는
구조라 이것도 언젠가 캐싱이나 증분 계산이 필요해질 것이다.

> `get_model()`에서 이미 썼던 "무거운 리소스는 전역에 한 번만 캐시한다"는
> 패턴이 같은 파일의 다른 함수(`get_collection()`)엔 안 적용돼 있었다.
> 9·10번 항목의 교훈과 같은 모양이다 — **한 곳에서 세운 원칙이 다른
> 함수에는 자동으로 안 따라간다.** 새 함수를 만들거나 기존 함수를 볼 때마다
> "이것도 그 원칙을 지키고 있는가"를 따로 확인해야 한다.

## 12. 새로고침할 때마다 대시보드가 다시 느려지는 문제 — 11번에서 남겨둔 숙제 + 새로 발견한 두 겹

**Situation**
"브라우저 새로고침할 때마다 데이터 로딩을 다시 하는 것 같다, 그래서 느리다"는
사용자 보고가 있었다. 11번 항목에서 이미 "`build_stats()`는 여전히 매 요청마다
전체 metadata를 캐시 없이 다시 훑는다"를 미해결로 남겨뒀던 바로 그 지점이다.

**Task**
감으로 어디가 느린지 짚지 않고, 대시보드가 새로고침 시 실제로 호출하는
엔드포인트 4개(`/api/stats`, `/api/digest`, `/api/timeline/{date}`,
`/api/conversations`)를 `curl` + `time`으로 하나씩 재서 병목을 먼저 특정했다.

**Action**

1. **엔드포인트별 실측**으로 범인을 좁혔다.
   ```
   /api/digest?n=5           3.98초   ← 압도적으로 느림
   /api/stats                0.51초
   /api/timeline/2026-08-03  0.04초
   /api/conversations        0.00초
   ```

2. **`/api/digest`가 4초 가까이 걸리는 원인**: "최근 기록" 카드가 매번
   `summarize_day(오늘 날짜)`를 부르는데, `summary_cache.is_cacheable_day()`는
   "오늘은 하루 종일 자라니까 캐시하지 않는다"는 원칙대로 오늘 날짜는 캐시를
   아예 안 보고 **매번 실제 LLM 호출**을 한다. 새로고침 한 번 = LLM 호출 한 번.

3. **11번에서 남겨둔 숙제를 처리했다**: `build_stats()`가 여전히 이벤트
   18,000개+를 매번 `col.get(include=["metadatas"])`로 전량 조회해 Counter를
   여러 번 순회하고 있었다. `col.count()`는 metadata를 안 읽고도 즉시 나오는
   값이라, 지난번 계산 때의 개수와 같으면(=색인이 새로 안 돌았으면) 계산
   결과를 그대로 재사용하도록 [stats.py:87-101](../src/screenlog/stats.py)에
   캐시를 얹었다.

4. **세 번째 원인은 계측 도중 우연히 드러났다.** `/api/digest`가 "최근 n일이
   며칠인지" 알아내려고 `indexed_dates()`를 따로 불렀는데, 이 함수도
   `col.get(include=["metadatas"])`로 전체를 또 스캔하고 있었다 — 3번에서
   막 캐싱한 `build_stats()`와 완전히 같은 스캔을 한 번 더 하는 중복이었다.
   `indexed_dates()`를 없애고 이미 캐시된 `build_stats()["dates"]`를 그대로
   재사용하도록 고쳤다([api.py:129](../src/screenlog/api.py)).

5. **오늘 날짜 LLM 호출(2번)은 디스크 캐시로 못 푼다** — "오늘은 캐시 안 함"
   원칙 자체를 어기게 되기 때문이다. 대신 API 프로세스 메모리에만 3분짜리
   짧은 캐시를 별도로 얹었다([api.py:98-114](../src/screenlog/api.py)).
   ```python
   _TODAY_DIGEST_TTL = 180
   _today_digest_cache = {}   # {date: (계산시각, 텍스트)}

   async def _digest_text(date):
       if summary_cache.is_cacheable_day(date):
           return await summarize_day(date)
       now = time.monotonic()
       cached = _today_digest_cache.get(date)
       if cached and now - cached[0] < _TODAY_DIGEST_TTL:
           return cached[1]
       text = await summarize_day(date)
       _today_digest_cache.clear()   # 자정 넘어가면 어제 항목은 버린다
       _today_digest_cache[date] = (now, text)
       return text
   ```
   `summary_cache.sqlite`(영구 저장)에는 손대지 않았다 — "오늘은 계속
   자란다"는 설계 의도는 그대로 두고, 그 프로세스가 떠 있는 3분 동안만
   같은 계산을 반복하지 않게 하는 얕은 캐시를 하나 더 얹은 것뿐이다.

**Result**

| | 수정 전 | 수정 후 |
|---|---|---|
| `/api/stats` | 1.70초(첫 호출도 느림) | **0.01초** |
| `/api/digest?n=5` | 3.98초 | **0.03초**(캐시 만료 후 첫 호출도) |
| 새로고침 체감 | 매번 4초+ | **0.03초대** |

세 겹의 원인이 서로 다른 성격이었다 — 하나는 "완전히 안 바뀌었으면 재계산
생략"(count 비교, 정확도 손실 없음), 하나는 "정확하게는 매번 새로 계산해야
맞지만 몇 분의 오차는 감수한다"(TTL), 하나는 "이미 하고 있는 스캔을
중복해서 또 하고 있었다"(재사용). 셋 다 같은 증상("느리다")으로 뭉뚱그려
보였지만 원인과 해법은 전혀 달랐다.

> 11번 항목이 "지금은 0.5초라 안 급하다"고 미뤄뒀던 캐싱이, 다른 문제
> (오늘 날짜 LLM 재호출)와 겹치면서 사용자가 체감하는 순간에는 결국
> 4초대로 합쳐져 있었다. **당장 안 급해 보여서 미뤄둔 성능 이슈도, 나중에
> 다른 병목과 겹치면 그제서야 사용자에게 보이는 증상 하나로 뭉쳐서
> 나타난다** — "지금은 괜찮다"와 "앞으로도 괜찮다"는 다른 말이다.
