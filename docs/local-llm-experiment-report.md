# 로컬 LLM 전환 실험 리포트

## 배경 / 목적

Screenlog은 원래 게이트웨이 API(`gemini-3.1-flash-lite`)로 라우팅·요약·에이전트
tool-calling을 처리한다. 비용 절감 및 로컬 배포 가능성을 검증하기 위해, 이미
OpenAI 호환 클라이언트 구조(`BASE_URL`/`API_KEY`/`CHAT_MODEL` 세 값만 교체하면
되는 구조)로 되어 있던 걸 활용해 [config.py](../src/screenlog/config.py)에
`USE_LOCAL_LLM` 스위치를 추가하고, Ollama로 로컬 모델을 붙여 실사용 품질을
비교했다.

## 실험 설계

- **평가 방식**: 처음엔 단일 날짜(8/4) 질문 5개로 얼추 비교했으나, "표본이 너무
  좁고 숫자 지표로는 실제 품질을 못 본다"는 문제 제기로 방식을 바꿨다 —
  **날짜/질문 수를 늘리고, 실제 답변 텍스트를 나란히 읽고 판단**하는 방식으로
  확정했다.
- **최종 벤치마크셋**: 검색 2 / 정리 3(희소·밀집·시간필터) / 비교 1 / 집계 1 /
  복합(에이전트 tool-calling) 1 = **8개 질문 × 밀도가 다른 5개 날짜**(17개~
  3,190개 이벤트, 이벤트 밀도가 요약 방식에 영향을 주는지 보기 위해 의도적으로
  희소~밀집을 고르게 섞음)
- **비교 대상**: API(`gemini-3.1-flash-lite`) vs 로컬 3종
  (Qwen2.5-7B, Qwen2.5-14B-Instruct-Q3_K_M, Llama3.1-8B-Instruct)
- **환경**: MacBook (Apple M2 Pro, 16GB 유니파이드 메모리), Ollama 로컬 서빙

## 단계별 결과

### 1단계 — Qwen2.5-7B-Instruct (Ollama 기본 양자화)

- 라우팅(`response_format` strict JSON schema)과 tool-calling(`agent.py`
  ReAct 루프) 자체는 정상 동작 확인.
- "정리" 유형에서 **하루의 극히 일부(5% 미만)만 요약**하는 패턴 발견 —
  8/4(2,144개 이벤트, 14:53~23:59) 질문에 저녁 시간대 5개 항목만 답함.
- 이벤트가 희소한 날(7/26, 실제 이벤트 범위 21:03~21:05)에서는
  **존재하지 않는 시각을 지어냄**(단순 누락이 아니라 환각).
- 검색 질문에서 같은 항목 중복 나열, 복합 질문(정리+슬랙초안)에서 슬랙 도구
  호출을 포기하고 실패하는 사례도 발견.

### 2단계 — Qwen2.5-14B-Instruct-Q3_K_M (크기를 키우면 나아지는가)

- M2 Pro 16GB에서 로드 시 시스템 여유 메모리가 1.8~4GB까지 빠듯해짐(모델
  자체가 7.9GB).
- **하루 커버리지 문제가 동일하게 재현됨** — 8/3 질문에 7B와 14B 둘 다
  21:28~21:50만 답함. 모델 크기로 해결되는 문제가 아님을 확인.
- **새로운 문제 발견**: 비교 질문에서 한국어로 답하다 중국어로 전환되는
  **언어 붕괴** 현상 — 공격적 양자화(Q3_K_M)가 다국어 안정성을 해친 것으로
  추정.
- 속도는 3배가량 느려짐(질문당 평균 18.6s → 58.5s). 유일한 개선은 복합
  질문(에이전트) 완주(7B는 실패했었음).
- **결론: 모델을 키워도 순이익이 없고, 오히려 언어 붕괴라는 새 리스크만
  추가됨.**

### 3단계 — Llama3.1-8B-Instruct (다른 계열이면 나아지는가)

- Qwen 계열 고유의 약점인지, 7~8B급 로컬 모델 전반의 한계인지 구분하기 위해
  비슷한 크기의 다른 계열을 테스트.
- **Qwen보다 전반적으로 더 나쁨**:
  - 비교 질문에서 존재하지 않는 연도(2022년)를 만들어내는 환각
  - "정리" 질문(7/26)에서 물어보지도 않은 다른 날짜(7/19~7/23)로 라우팅이 샘
  - 집계 질문(LLM을 안 거치는 결정론적 경로임에도) 라우팅 자체가 실패해
    "기록에 없습니다"로 답함
  - 검색 질문에서 질문 문장을 그대로 답변에 되풀이하는 등 포맷 붕괴
- 유일한 우위: 8/3 밀집일 정리에서 시간 커버리지가 Qwen7B보다 조금 넓었던 것,
  복합 질문 완주.
- **결론: Qwen만의 약점이 아니라 7~8B급 로컬 모델 전반의 한계에 가깝다.**
  한국어 학습 비중이 상대적으로 강한 Qwen 계열이 그나마 나은 축이었다.

### 4단계 — LoRA 파인튜닝 (Qwen2.5-7B, 지식 증류)

**가설**: recency bias는 지식 부족이 아니라 "긴 컨텍스트의 뒷부분에만 집중하는
행동 습관"이다. 그렇다면 소수의 예시로 행동을 교정하는 LoRA로 고칠 수 있는지
검증한다.

**정답(teacher label) 선정 근거**: API가 더 크고 비싸서가 아니라, 원본
이벤트(`browse()`)와 대조해서 **인용 시각이 실제 이벤트 범위와 일치함을 이미
검증**했기 때문에 API 출력을 정답으로 썼다(지식 증류/distillation).

**데이터셋 v1 → v2**: 처음 38개(하루/시간대 슬라이스만)는 "하루 전체"와 특정
슬라이스가 사실상 같은 이벤트를 보는 가짜 중복이 많았다. 슬라이스가 하루
이벤트의 90% 이상을 차지하면 건너뛰는 로직을 추가하고, 앱 필터·질문 표현
변형·비교/인수인계/슬랙 프롬프트 유형까지 축을 늘려 **68개**로 재구성했다
([eval/generate_lora_dataset.py](../eval/generate_lora_dataset.py)). held-out
날짜(7/26·8/3·8/4)는 전 과정에서 학습 데이터로 한 번도 쓰지 않았다.

| 학습 데이터 유형 | 개수 |
|---|---|
| 정리(하루/시간대) | 36 |
| 정리(질문변형: 자세히/쉽게) | 8 |
| 정리(앱필터) | 6 |
| 비교 | 10 |
| 인수인계 | 3 |
| 슬랙 | 5 |
| **합계** | **68** |

**held-out 평가셋**: 정리 3(전일) + 시간대 슬라이스 2 + 비교 1 + 슬랙 1 = **7개**
([eval/generate_heldout_eval.py](../eval/generate_heldout_eval.py)). 목표
능력(정리)뿐 아니라 다른 능력이 파인튜닝으로 망가지는지(catastrophic
forgetting)도 같이 봤다.

**표본 크기에 대한 정직한 평가**: 학습 68개, 검증 7개 전부 **원천 14일치
로그**(11일 학습 + 3일 검증)에서 파생됐다 — 검증 7개 중 5개(커버리지를 숫자로
잰 것)도 실제로는 8/3·8/4 두 날짜를 하루 전체/시간대 슬라이스로 두 번씩 잰
것이라, 완전히 독립적인 정보량 기준으로는 7/26·8/3·8/4 **세 날짜**에 가깝다.
검증을 늘리려면 학습 데이터를 그만큼 줄여야 하는 트레이드오프라(원천이
고정된 14일이므로) 지금 시점엔 늘리기 어렵다. 다만 관측된 효과 크기가 크다는
점(예: 0.03→0.95, 30배 가까운 변화)은 표본이 작아도 우연으로 보기엔 폭이
크다는 근거는 된다 — "통계적으로 확실하다"가 아니라 "표본은 작지만 방향성은
신뢰할 만하다" 정도로 해석해야 한다.

**학습 구현 중 실제로 겪은 문제들** (전부 "에러 없이 조용히 망가지는" 유형이라
중요):
- `trl.SFTTrainer`가 라이브러리 버전마다 API가 바뀌어 세 번 연속 다른 이유로
  깨짐 → `trl` 자체를 버리고 안정적인 `transformers.Trainer` + `peft.get_peft_model()`로
  직접 구현.
- Colab 사전 설치된 `torchao`가 `peft` 요구 버전보다 낮아 `ImportError` → 미사용
  패키지라 제거.
- **토큰 길이 함정**: 프롬프트 중앙값이 14,394 토큰(한국어 토큰 비효율 + 이벤트
  60개). `max_length=8192` 같은 흔한 기본값으로 자르면 68개 중 46개(68%)에서
  **정답이 통째로 잘려 학습 신호가 0**이 됐을 것 — 학습은 정상 종료되지만
  아무것도 안 배운 상태. 사전에 길이 분포를 재고 `max_length=17408`로 전부
  담기게 조정해서 회피.
- **마스킹 경계 버그**: "프롬프트 토큰 길이만큼 앞을 마스킹"하는 흔한 방식은
  토큰화가 prefix를 보존하지 않아 경계가 밀렸다(`assistant\n`의 개행이 뒤따르는
  한국어 첫 글자와 한 토큰으로 병합됨, 실측으로 `assert` 실패시켜 발견). 프롬프트와
  정답을 각각 토큰화해 이어붙이는 방식으로 수정.
- **OOM 위험**: 16K 토큰 시퀀스에서 전 위치 logits를 계산하면 손실 계산+backward만
  20GB를 넘겨 A100 40GB로도 위험. 정답이 시퀀스 끝에 몰려 있다는 성질을 이용해
  끝부분 logits만 계산하는 `TailLossTrainer`를 구현하고, 소형 모델로 기본 구현과
  손실이 1e-6 오차 내 수학적으로 동일함을 직접 검증한 뒤 반영.

**결과 — bf16(Colab, 파인튜닝 직후)**: held-out 5개 커버리지 중 2개 뚜렷한
개선(8/4 전체 0.05→0.42, 8/3 12~18시 0.38→0.91), 1개 거의 그대로(8/3 전체
0.85→0.94), 1개 소폭 악화(8/4 18~24시 0.65→0.56), 1개는 좁은 시간창이라 숫자가
오히려 오독을 부르는 케이스(7/26 1.00→0.50이지만 실제로는 포맷이 GOLD처럼
개선된 것 — 원본이 이벤트를 초 단위로 그냥 나열해서 우연히 커버리지가 높았을
뿐). **"방향성은 있으나 완전한 해결은 아니다"로 결론.**

**결과 — Q4_K_M 양자화(실사용 형태) 재검증**: bf16 결과와 정밀도 변수를
없애기 위해, 병합 → GGUF 변환 → `llama-quantize`로 Q4_K_M 양자화까지 끝내고
Ollama에 등록해 **원본(양자화) vs LoRA(양자화)**를 다시 비교했다. 결과는
훨씬 더 극적이었다:

| 항목 | 원본(양자화) | LoRA(양자화) | GOLD |
|---|---|---|---|
| 정리(7/26, 희소) | 1.00 | 0.50 | 1.00 |
| 정리(8/3, 밀집) | 0.03 | 0.95 | 0.98 |
| 정리(8/4, 밀집) | 0.13 | 0.77 | 0.97 |
| 정리(8/3, 12~18시) | 0.03 | 0.92 | 0.95 |
| 정리(8/4, 18~24시) | 0.02 | 0.95 | 0.95 |

양자화된 원본이 bf16보다 훨씬 심하게 망가져 있었는데(0.02~0.13 vs bf16
0.05~0.85), LoRA가 그 격차를 대부분 메꿨다. 내용도 확인했다 — 실제 활동(Finder,
카카오톡, 줌 회의, GitHub, AWS)을 정확히 짚었고, 비교/슬랙 결과도 GOLD와 결론이
일치했으며 환각·언어 오염 없이 정상 작동했다.

**결론**: 68개라는 작은 데이터셋(원천 14일 제약)에도 불구하고, **실사용 형태(양자화)에서
GOLD에 근접하는 수준까지 개선을 확인했다.** bf16 테스트만 봤다면 "부분적
개선"에 그쳤을 결론이, 실제 배포 조건까지 맞춰보니 훨씬 강한 결과로 나왔다 —
평가 환경(정밀도)을 실사용 조건과 맞추는 게 왜 중요한지 보여주는 사례.

### 5단계 — 프롬프트 분할(아키텍처 수준 해법, 파인튜닝 대안)

**아이디어**: 모델 가중치는 전혀 안 건드리고, 호출 방식만 바꾼다. 하루를
6시간 블록 4개로 나눠 블록마다 따로 요약(map)한 뒤 합치는(reduce) 방식 —
`summarize_range()`가 "여러 날짜"에 이미 쓰던 패턴을 "하루 안 시간대"로 한
단계 더 세분화한 것. `summarize.py`는 전혀 수정하지 않고
[eval/experiment_chunked_summary.py](../eval/experiment_chunked_summary.py) 등
별도 실험 스크립트로만 검증했다.

**v1 — 단순 이어붙이기(reduce 없음)**: 커버리지가 압도적으로 개선됐다
(8/3 0.03→0.81, 8/4 0.13→1.00, GOLD 0.97~0.98). 다만 호출 횟수가 늘어난 만큼
(1회 → 3~4회) **그중 한 번이라도 이상 동작할 확률이 누적**됐고, 실제로 한
블록이 한국어 대신 중국어로 응답했다. 이 오염이 이어붙이기를 통해 그대로
저장되고, 이 결과를 입력으로 쓰는 비교/인수인계/슬랙까지 전파돼 하위 기능
결과물이 중국어로 오염됐다.

**v2 — LLM reduce 추가**: 블록 요약들을 "한국어로만 다시 정리해달라"는 LLM
호출로 한 번 더 합쳤다. 결과는 기대와 반대였다 — (a) 모델이 번역 지시를
신뢰성 있게 따르지 않아 오염이 그대로 통과됐고(8/3), (b) reduce 호출 자체가
"블록 4개를 합친 긴 컨텍스트"라 **recency bias를 그 안에서 재도입**해 커버리지가
오히려 악화됐다(8/4: 1.00→0.19). **"긴 컨텍스트를 한 번에 재처리"라는 접근
자체가 재귀적으로 같은 문제에 걸린다는 것을 확인.**

**v3 — 오염된 블록만 타겟 재시도**: reduce(전체 재작성) 대신, 블록별 결과를
검사해서 비한국어가 5자 이상 섞인 블록만 좁게 재호출(프롬프트에 "반드시
한국어로만" 지시 추가 + temperature 조정)했다. 결과:

| 항목 | 커버리지 | 언어 오염 |
|---|---|---|
| 8/3 (1개 블록 재시도) | 0.81 | 없음 |
| 8/4 (재시도 불필요) | 1.00 | 없음 |

비교("8/3이 더 바쁨", GOLD와 결론 일치)와 슬랙 초안(자연스러운 한국어, 실제
활동 기반)도 정상 작동을 확인했다.

**부가 확인**: 라우팅(정리/비교/집계 intent 분류)은 이 변경과 무관하게 정상
작동. 에이전트(`screenlog_langgraph.agent`, 복합 질문)는 `summarize.py`를
안 건드렸으므로 여전히 기존 버그(21:28~21:48만 답함)를 그대로 재현함 —
아직 프로덕션에 연결 안 했다는 대조군 확인.

**결론**: GPU도 학습 데이터도 없이, **코드만으로 LoRA와 동등하거나 더 나은
결과**를 얻었다. 단, "블록별 호출 후 이상 블록만 재시도"까지 구현해야
안정적이다(단순 이어붙이기나 통째 reduce는 둘 다 실패).

## 종합 결론

| 시도 | 판정 |
|---|---|
| 모델 크기 키우기 (7B → 14B) | 효과 없음, 언어 붕괴라는 새 리스크만 추가 |
| 모델 계열 바꾸기 (Qwen → Llama) | 오히려 더 나쁨 |
| LoRA 파인튜닝 (68개, 양자화 형태) | **효과 있음** — GOLD 근접, 호출 1회로 빠름. 단 학습 데이터 준비·GPU·디버깅 비용 큼 |
| 프롬프트 분할 + 오염 블록 재시도 | **효과 있음** — GOLD 근접, 학습 불필요. 단 호출 3~5배, 재시도 로직 필요 |
| 근본 원인 | 긴 컨텍스트를 지시대로 고르게 훑는 능력 자체가 이 체급(7B) 로컬 모델의 공통 한계였으나, **모델을 그대로 둔 채로도(분할) 또는 좁게 교정해서도(LoRA) 둘 다 실용적으로 해결 가능함을 확인** |

`USE_LOCAL_LLM` 환경변수 하나로 API/로컬을 즉시 전환할 수 있게 설계해뒀기
때문에([config.py](../src/screenlog/config.py) 참고), 두 해법 중 하나를
프로덕션에 반영하더라도 코드 변경 없이 롤백 가능하다. **아직 `summarize.py`
자체에는 반영하지 않은 상태**(전부 `eval/` 밑 별도 실험 스크립트로만 검증) —
다음 단계로 실제 적용이 남아있다.
