# screenlog

screenpipe가 쌓아둔 화면 기록에 질문해서 답을 얻는다.

## 왜 바닐라부터 시작하는가

교과서 RAG(프레임 텍스트 → 청킹 → 임베딩 → top-k → LLM)가 이 데이터에서
**얼마나 안 되는지**를 먼저 숫자로 본다. 베이스라인 없이 개선하면
"좋아진 것 같다"만 남고 "얼마나 좋아졌다"는 못 말한다.

바닐라는 버릴 코드가 아니라 **비교 기준**이다. 0단계 결과를 지우지 않는다.

## 단계

각 단계는 통과 기준을 넘기 전에 다음으로 가지 않는다.
기준을 못 넘으면 다음 기능을 얹어도 그 효과를 잴 수 없기 때문이다.

| 단계 | 무엇 | 통과 기준 |
|---|---|---|
| **0. 바닐라** | sqlite → 프레임 그대로 색인 → 검색 → LLM | 질문 하나에 답이 나온다. 답이 틀려도 통과 |
| 1. 정제 | 프레임 → 이벤트 (연속 중복 접기) | 무작위 20건을 읽었을 때 "아 이때 이거 했지"가 읽힌다 |
| 2. 메타 필터 | app/hour/date를 metadata로 | `where`로 앱 지정 검색이 된다 |
| 3. 라우팅 | 질문에서 필터 뽑기 | 앱 지정 질문 정확도가 0단계보다 오른다 |
| 4. 조회 | "오늘 뭐 했지" = 검색이 아니라 조회 | 하루 요약에 여러 앱이 등장한다 |
| 5. 하이브리드 | 키워드 검색 + 벡터, 순위 융합 | 고유명사 질문에서 벡터 단독보다 낫다 |
| 6. 서비스 | 웹 UI | — |

## 규칙

**실험은 하루치로 한다.** 전체 색인은 결론이 난 뒤 한 번만 돌린다.
전량 임베딩은 10분 넘게 걸리고, 하루에 여러 번 재실험할 수 있는지가
실제로는 진행 속도를 결정한다.

**원본을 복사하지 않는다.** `~/.screenpipe/db.sqlite`를 읽기 전용으로 직접 읽는다.
덤프 사본을 만들면 원본이 자란 뒤 사본이 뒤처져, 결과가 어느 시점 데이터인지
알 수 없게 된다.

**숫자를 남긴다.** 터미널에만 뜬 숫자는 다음 날이면 사라진다.

## 데이터 / 개인정보

화면 기록에는 메신저 대화와 로그인 화면이 들어있다.
`chroma/`와 `.env`는 커밋되지 않는다. 공개 데모를 만들 때는
앱 화이트리스트를 먼저 정한다.

## 실행

uv sync
cp .env.example .env    # API 키 채우기
